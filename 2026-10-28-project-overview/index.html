Three components. The public part lives on a small VPS and knows nothing about the court. fc-api sits on a court server and pulls filings out, polling every few seconds; the connection always starts inside the court. Madhoshi holds the private key, so a full copy of the VPS, disk and backups, reveals no filing content.

Architecture

Four rules behind the picture

Outbound only

fc-api calls out to the VPS. The VPS never calls in. The whole class of “attacker reaches the court network through the integration” goes away.

Sealed at rest

Each filing is encrypted with the court’s public key the moment it is validated. In clear on the VPS: reference, form code, hashed phone, status, times. Nothing else.

Two-step acknowledgement

fc-api confirms to the VPS once it holds a sealed copy; the VPS deletes. Madhoshi confirms to fc-api once decrypted and stored; fc-api drops its copy. Nothing is kept longer than needed.

Forms are data

One versioned schema per form drives the web form, the validation and the display in Madhoshi. Court reviewers sign off each version. Nobody re-implements a form by hand.

Family Court eForms · 28 October 2026 · 5

If you remember four things from the architecture, these are the four. Each one answers a risk on the register: outbound-only answers R02, sealing answers R01, the two-step acknowledgement keeps the public server nearly empty, and forms as data keeps the wording under the court’s control.

Dhivehi and English. Drafts stay in the browser, never on the server.

Validated against the schema, then encrypted with the court’s public key.

The phone proves a contact, not the applicant. Staff verify the applicant in Madhoshi from the ID card image, selfie and signature inside the sealed filing. eFaas comes in a later release.

Why a framework

Plain JavaScript or Next.js, for this project

Plain JavaScript, as the prototype is

For

  • No build step, no toolchain to maintain
  • Almost no dependencies to whitelist or audit
  • Small download, runs in any browser
  • It exists today and works for 17 forms

Against

  • Every screen hand-wired: one 3,018-line engine holds all state
  • Output escaping by hand, in 65 places; one miss is an injection
  • No types: a wrong field key is found by a citizen, not the build
  • No tests, no page-weight budget; Dhivehi and right-to-left by hand
  • Conventions live in one person’s head; hard to hand over

Next.js with TypeScript, as Aailaa is

For

  • Components escape output by default; injection takes deliberate effort
  • Types and lint fail the build before a mistake ships
  • Field components and validation tested in isolation, run in CI
  • Per-form code splitting; a size budget enforced automatically
  • Locale files and right-to-left built in; static export, no server process
  • Same stack as Aailaa: shared components, easy to hand over

Against

  • Hundreds of packages: whitelist review, a bill of materials, monthly audits
  • A build toolchain to keep current; major upgrades take work
  • Bundles grow if nobody watches; the budget must be enforced
  • Framework conventions to learn for anyone new to it

For this project, Tier 1, 17 forms, one developer: the framework’s safe defaults are worth its dependency cost.

Family Court eForms · 28 October 2026 · 8

A fair comparison. Plain JavaScript is lighter and has real advantages, and the prototype proves it can be made to work. The case for Next.js is not that it is modern; it is that the things a Tier 1 audit checks are its defaults, and the cost, a larger dependency tree, is one the court already pays and manages on Aailaa.

Why rebuild

What we carry over, and what we leave

Carried over as content and design

  • The 17 form specs: fields, steps, Dhivehi wording, shared modules. Re-checked against the paper forms, then converted to our schema format.
  • The citizen flow: reference number, contact phone, status page, returned-for-correction.
  • The OTP design: hashed code, five minutes, five tries, resend once a minute.
  • Upload rules learned the hard way: file type from the bytes, size caps, no execution.
  • The Dhivehi phonetic keyboard mapping and the date and phone conventions.

Left behind

  • The code itself, front end and backend. Nothing is copied across.
  • The admin panel. Staff work in Madhoshi, where sign-in, grants and audit already exist.
  • Filings stored readable on the public server. Ours are sealed before they are written.
  • Status by reference number alone. Ours needs the code to the verified phone as well.
  • A public server that can push into the court. Ours is only ever pulled from.

Databases

Three small stores, none shared, SQLite to start

VPS · fc-eforms store

Sealed blobs and routing metadata

Filing rows while waiting for collection: reference, form code, schema version, hashed phone, times, lease, key id, sealed payload, sealed attachments. Status records afterwards. Payload deleted on acknowledgement.

SQLite in WAL mode; sealed attachments as files in a service-only folder. No database server to harden on a public box. Postgres if production hosting provides one.

FC server · fc-api sync store

Not a database: a connector per source

fc-api reads whatever the court already has, each through its own connector and read-only credential: MySQL, MongoDB, Firebase, Google Sheets, CSV and JSON files, and the eForms link.

Its own store is small, SQLite to start: sealed filings awaiting Madhoshi, synced copies of sources that cannot be queried live, and the audit log of every read of personal data.

FC server · Madhoshi

The decrypted filings

Existing tables plus the eforms module: decrypted filings with their schema version, assignment, status history, messages. Attachments on disk.

SQLite, already in production. The private key is not in the database: Windows DPAPI or Credential Manager, an HSM later, and an offline backup held by two custodians.

Never in clear on the VPS: national ID numbers, names, addresses, case details, attachments, OTP codes. The contact phone is the one exception, kept encrypted with a VPS-local key because the server must send the code and the notifications.

Family Court eForms · 28 October 2026 · 13

Each component owns its data. The public store is nearly empty by design. The court copy in fc-api is still sealed. Madhoshi is where the data becomes readable, and it is already a production SQLite system, which is why SQLite is the recommendation everywhere to start.
